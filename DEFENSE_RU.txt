1. Linux и Bash
Linux — операционная система, в которой исполняются сервисы лабораторной.
#!/usr/bin/env bash выбирает Bash; аргументы доступны как $1, $2 и "$@".
pwd показывает каталог, ls -la включает скрытые файлы. mkdir создаёт каталог,
а mkdir -p также создаёт отсутствующих родителей и не ругается на готовый путь.
touch создаёт пустой файл или обновляет время изменения. cp копирует, mv
перемещает или переименовывает. Абсолютный путь начинается с /, относительный
считается от текущего каталога. df -h показывает занятое и доступное место,
free -h — память и swap. ps показывает процессы, PID однозначно указывает
процесс в данный момент; kill PID отправляет сигнал выбранному процессу.

> перенаправляет вывод с перезаписью файла, >> дописывает в конец.
tee сохраняет вывод и одновременно показывает его. tail -n 5 FILE выводит
пять последних строк, grep Suyubek FILE ищет фамилию. grep ... > analysis.txt
сохраняет найденные строки отдельно.

chmod меняет права. Для данного задания нужен 744: владелец rwx, остальные r--.
Это отличается от 755, где группа и остальные также имеют x. chmod +x делает
файл исполняемым, но не всегда устанавливает точный требуемый режим.

2. Git и GitHub
Git хранит версии локально; GitHub размещает удалённый репозиторий.
Рабочее дерево содержит файлы, staging area — подготовленные изменения,
репозиторий — коммиты. git add добавляет в staging, git commit фиксирует его.
git init создаёт репозиторий, git status показывает изменения/индексацию.
Ветка — указатель на линию истории. git switch -c NAME создаёт и выбирает её.
merge объединяет линии, сохраняя историю; rebase переносит коммиты на новую
базу и изменяет их SHA. Публичную общую историю без согласования не переписывают.
Конфликт возникает, когда Git не может совместить изменения автоматически.
Нужно прочитать обе версии, удалить маркеры, написать итог, git add и commit.
fetch загружает ссылки/коммиты; pull также интегрирует изменения. push
публикует локальные коммиты. При расхождении сначала status/fetch/log/diff,
затем осознанный merge/rebase, а не бездумный force push или reset --hard.
Тег — именованная метка версии; коммит — сам снимок изменений и метаданные.
.env и пароли нельзя коммитить: публичная история позволяет восстановить их
даже после удаления файла. .gitignore не удаляет уже отслеживаемые файлы.

3. Docker и PostgreSQL
Образ — шаблон файлов и настроек; контейнер — его экземпляр с состоянием.
FROM задаёт базу. WORKDIR задаёт рабочий каталог. COPY копирует входные файлы;
ADD имеет дополнительные возможности распаковки/источников, здесь они не нужны.
RUN исполняется при сборке, CMD/ENTRYPOINT — при старте. EXPOSE документирует
порт, но не публикует его. -p 127.0.0.1:8081:8080 связывает локальный порт Mac
с портом приложения в контейнере через проброс VM. docker build создаёт образ.
Многоэтапная сборка оставляет JDK/Gradle в build stage и переносит только JAR
в JRE runtime. Итоговый процесс исполняется как studentapi, не root.
stop завершает процесс, rm удаляет контейнер. logs показывает stdout/stderr,
exec запускает команду внутри работающего контейнера.

Compose описывает сервисы, зависимости, переменные, сеть и том. В нашем
проекте это app и db. localhost внутри app означает сам app, а не PostgreSQL.
Имя db разрешается DNS выделенной Docker-сети. pg_isready проверяет готовность
сервера принимать подключения; зависимости Compose ждут healthy. Полную
работоспособность приложения дополнительно подтверждают HTTP CRUD-запросы.
Сеть обеспечивает связь сервисов, том хранит данные вне файлового слоя
контейнера. down без -v сохраняет именованный том; down -v удаляет его.
Пароль поступает из приватного .env через environment, не из исходников.
Полный docker inspect/config может показать секреты, поэтому при демонстрации
используются отобранные поля и docker compose config --quiet.

Если app не подключается к БД: проверить compose ps/health, логи app/db,
hostname db, порт 5432, сеть и согласованность имени базы/пользователя/пароля.
Не публиковать секреты при такой проверке. Существующий PostgreSQL volume
хранит первоначально созданную роль: простая смена .env не меняет её пароль.

4. Jenkins и CI
Jenkins controller управляет задачами; агент выполняет команды. Здесь
исполнитель встроен в контроллер внутри учебной Ubuntu VM. Job — настроенная
задача, build — её отдельный запуск. Jenkinsfile — Pipeline в системе Git.
Declarative задаёт структуру pipeline/stages/steps; Scripted использует более
свободный Groovy. Checkout получает исходники. Build компилирует через Gradle,
Test запускает тесты, Docker Build создаёт персональный образ, Verify
проверяет его наличие, метаданные и совпадение OCI revision с Git SHA.
Gradle wrapper задаёт версию Gradle и SHA256 дистрибутива; агенту нужен JDK.
Docker CLI и доступный daemon нужны на агенте, иначе docker build не сработает.

Ненулевой код Gradle завершает стадию ошибкой, последующие обычные стадии
пропускаются. post always сохраняет XML тестов даже при failed test; он не
скрывает ненулевой результат. В контролируемой ветке ожидаемый ID специально
заменён на WRONG-ID-CONTROLLED: один из 16 тестов падает. После исправления
37773 все тесты проходят. В main эта ошибка не вносилась.

SCM polling проверяет Git на изменения по расписанию; cron без pollSCM
запускает задачу по времени независимо от изменений. GitHub webhook отправляет
Jenkins уведомление о событии; для локального Jenkins здесь выбран polling,
поэтому публичный входящий адрес/туннель не требуется. Причина автоматического
запуска подтверждается SCMTriggerCause, а не только зелёным значком.
Jenkins Credentials предназначены для секретов job. Наш публичный checkout
не требует credentials. Для private repo нужен ограниченный SSH key/token в
Credentials и credentialsId в SCM; секрет не записывается в Jenkinsfile.

CI автоматически объединяет проверку исходников, сборку и тесты.
Continuous Delivery готовит проверенный выпуск к развёртыванию с отдельным
решением о запуске. Continuous Deployment автоматически развёртывает каждый
успешный выпуск. В задании требуется CI и проверка образа; автоматическое
развёртывание не требуется. Compose-развёртывание показано отдельно.

5. Разбор ошибок
Если Gradle упал: открыть Console Output и XML/HTML test report, найти первую
причину, сверить JDK/Gradle/dependencies и воспроизвести wrapper-команду.
Если сборка Java прошла, а Docker Build нет: смотреть именно Docker stage,
проверить daemon access, Dockerfile, контекст, базовый образ, сеть и путь JAR.
В консоли должны быть имя студента, SHA, команды, ошибки и итоговый статус.
Сначала читают реальную причину; ошибки не маскируются через || true.
